เลิกจำว่าใครพาผู้เล่นมา — ตัดสินใหม่ทุกครั้งที่เข้าเล่น

มติเปลี่ยนวิธีคิดส่วนแบ่งพาร์ตเนอร์ ให้ตรงกับที่ทั้งตลาดเว็บเกมใช้กันอยู่

เปลี่ยนอะไร

เดิม

จำไว้ว่าผู้เล่นคนนี้ dev เป็นคนพามา แล้วจ่ายเรตสูงให้ dev ทุกครั้งที่เขากลับมาเล่นเกมนั้น ต่อไปอีก 12 เดือน

ใหม่

ดูทุกครั้งที่เข้าเล่นว่า ครั้งนี้มาจากช่องทางใคร — ช่องทางนั้นได้เรตสูงของครั้งนี้ จบในตัว ไม่ต้องจำ

ทำไม

ตลาดทำแบบนี้หมด

ไม่มีเว็บเกมเจ้าไหนเก็บบัญชี “ใครหาคนนี้มา” พาร์ตเนอร์ที่เคยอยู่กับ Poki หรือ GameDistribution จะเข้าใจทันทีโดยไม่ต้องอธิบาย

ย้อนกลับได้ไม่เท่ากัน

ให้น้อยแล้วเพิ่มทีหลัง พาร์ตเนอร์ดีใจ · ให้มากแล้วหดทีหลัง พังความสัมพันธ์ถาวร ถ้าจะเสี่ยง ต้องเสี่ยงข้างที่ถอยได้

ทีมไม่ว่าง

โปรแกรมพาร์ตเนอร์สร้างปี 2027 เปิดปี 2028 แต่ของที่ต้องเสร็จคือ SDK 25 ก.ย. · พอร์ทัลเฟส 1 วันที่ 1 ต.ค. · Festa 7 พ.ย.

กติกาใหม่ทั้งหมด

สั้นแค่นี้จริง ๆ และความสั้นคือจุดขาย:

  1. ลิงก์ของพาร์ตเนอร์ผูกกับเกม — ?ref=partnerID&g=gameID&c=channel เซ็น HMAC รวมทั้งก้อน
  2. ทุกครั้งที่เข้าเล่น ระบบดูว่ามาจากไหน แล้วตัดสินเรตของครั้งนั้นทันที
  3. lookback 7 วัน — คลิกลิงก์วันนี้ เปิดเล่นภายใน 7 วัน ยังนับให้พาร์ตเนอร์ (มาตรฐานเดียวกับ AppsFlyer/Meta)
  4. ผูกกับเกม ไม่ข้ามเกม — ลิงก์เกม A ไม่ให้เครดิตตอนผู้เล่นไปเล่นเกม B

ต่างกันจุดเดียวคือวันอังคาร — วันที่ผู้เล่นกลับมาเอง ไม่ได้มาจากช่องทางใคร โมเดลเดิมยังจ่าย 75% เพราะจำได้ว่า Studio X เป็นคนหามา โมเดลใหม่จ่าย 50% เพราะครั้งนี้ ROPZ เป็นคนพามาเจอเกม

อะไรหายไป

ของเดิมทำไมไม่ต้องมีแล้ว
ตาราง attribution ต่อ (ผู้เล่น × เกม)ไม่ต้องจำอะไรข้ามครั้ง จึงไม่มีอะไรให้เก็บ
นาฬิกา 12 เดือน + ต่ออายุเรตตัดสินรายครั้ง ไม่มีอายุให้หมด
state machine PENDING → CONFIRMED / EXPIRED / REJECTEDมีไว้กันคนปลอมยอดเข้าบัญชีถาวร พอไม่มีบัญชีก็ไม่มีอะไรให้ปลอม
ด่านคุณภาพ 7 วัน (2 ชั้น A/B)เหลือแค่กันบอตระดับ ad-fraud ปกติ ซึ่งเครือข่ายโฆษณาทำให้อยู่แล้ว
clawback 60–90 วันไม่เคยจ่ายล่วงหน้าบนความจำ จึงไม่มีอะไรต้องเรียกคืน
guest → register merge, mixed-touch, true-up ย้อนหลังเคสพวกนี้เกิดจากการพยายามผูกคนกับความจำ

นาฬิกาเหลือ เรือนเดียว จาก 5 เรือน · ลดงานหลังบ้านและลดพื้นที่ PDPA ที่ต้องดูแล เพราะไม่ต้องเก็บว่าใครถูกใครชวนมา

แลกอะไรไป — ข้อเสียที่ต้องยอมรับ

พาร์ตเนอร์ได้น้อยลงจริงในกรณีเดียว — ผู้เล่นที่เขาอุตส่าห์ดึงมา ถ้าเดือนหน้ากลับมาเองทางหน้าแรก ROPZ พาร์ตเนอร์จะไม่ได้เรตสูงของครั้งนั้น จุดขาย “พาชุมชนมาสิ แล้วกินยาว” อ่อนลง

แลกกับการที่พาร์ตเนอร์เข้าใจโมเดลทันทีเพราะเหมือนที่เขาเจอมาแล้ว และเราเติมความจำให้เป็นดีลพิเศษรายเจ้าได้เสมอถ้าวันหนึ่งอยากดึงพาร์ตเนอร์ใหญ่

เรตยังเท่าเดิม

มตินี้เปลี่ยน วิธีตัดสินว่าใครได้เรตไหน อย่างเดียว ตัวเลขไม่ได้แตะ — dev-brought ยัง 75/25 · ROPZ-brought ยัง 50/50 · ชั้น royalty T0–T4 (0/3/8/15/25%) และชั้นคูปองยังเหมือนเดิมทั้งหมด

ต้องตามแก้ที่ไหนบ้าง

  1. ROPZ_Attribution_RevShare_Spec / Dev / Exec / Explainer — ตัดหัวข้อนาฬิกา 5 เรือน ด่านคุณภาพ และ clawback ออก เหลือ lookback 7 วัน
  2. ROPZ_DevBrought_Deck_v2 — สไลด์ “นาฬิกา 5 เรือน” และ “ด่านคุณภาพ” ตกไปทั้งสองหน้า · ข้อความ k10 (“คิดแยกเป็นรายผู้เล่น”) และ k20 (“75% อยู่ได้ 12 เดือน”) ต้องเขียนใหม่ ทั้ง 4 ภาษา
  3. ไฟล์บน GitHub Pages — 4 ไฟล์ในชุด attribution ต้องอัปตาม
  4. P&L — ทิศทางคือส่วนแบ่งไหลกลับมาหา ROPZ มากขึ้น ตัวเลขน่าจะดีขึ้น รันรอบหน้าพอ ไม่ใช่ตัวขวางมติ

ยังไม่เคาะ

  • lookback 7 วัน เป็นข้อเสนอตามมาตรฐาน AppsFlyer/Meta — ยังปรับได้ก่อนเขียนลงสัญญา
  • ลิงก์ฝังเว็บ dev — ถ้าเกมถูกฝังบนเว็บ Studio X เอง ทุกครั้งที่เล่นบนนั้นถือเป็น dev-brought อัตโนมัติหรือไม่ (Poki ตอบว่าใช่) ควรเคาะพร้อมกัน
