รายการที่ต้องต่อ — ฝั่ง Unity และฝั่ง Backend

ทุกอย่างในหน้านี้มาจากกฎข้อเดียว: เซิร์ฟเวอร์ของ ROPZ เป็นผู้ตัดสิน ตัวเกมเป็นผู้ส่งสัญญาณ · ระบบตั้งค่าเริ่มต้นว่า ROPZ เป็นคนพาผู้เล่นมา — ถ้าคุณไม่ส่งสัญญาณอะไรเลย ระบบไม่มีทางรู้ว่าคุณเป็นคนพามา และคุณจะได้เรตของฝั่ง ROPZ ทั้งที่ออกแรงหาผู้เล่นเอง · สิ่งที่ต้องเพิ่มเกือบทั้งหมดคือการส่งหลักฐาน ไม่ใช่การคำนวณเงิน (การคำนวณเงินเป็นงานฝั่งเรา)

ของที่ ROPZ ทำให้แล้ว — คุณไม่ต้องทำเอง: ตัดสินว่าใครพาผู้เล่นมา · ด่านคุณภาพและการกันบอต · คิดเรตและแบ่งเงิน · กระเป๋าเพชรและการรับชำระเงิน · แดชบอร์ดตัวเลข · การจ่ายเงินและเอกสารภาษี · อย่าทำระบบเหล่านี้ซ้ำเอง เพราะตัวเลขจะไม่ตรงกัน แล้วต้องมานั่งเถียงกันทีหลังว่าของใครถูก

1 · ฝั่ง Unity (ตัวเกม)

ต้องเพิ่มอะไรทำอะไรบ้างทำไมต้องมี — ถ้าไม่ทำจะเกิดอะไร
ROPZ SDK + session_startเรียกตอนเปิดเกมทุกครั้ง · ส่ง ref / referrer / campaignId ที่ติดมากับ URL ต่อให้เซิร์ฟเวอร์เป็นสัญญาณเดียวที่บอกได้ว่าใครพาผู้เล่นคนนี้มา · ไม่ส่ง = ตกเป็นค่าตั้งต้น ROPZ พามา → โฆษณาได้ 50/50 แทน 75/25
heartbeat ทุก 30 วินาทีส่ง playSecCumulative · นับเฉพาะตอนเล่นจริง หยุดนับตอนหยุดเกมหรือแท็บถูกซ่อนใช้พิสูจน์ชั้น B ของด่านคุณภาพ (เล่นจริง ≥ 60–90 วินาที) · ไม่ส่ง = ผู้เล่นที่คุณพามาไม่ผ่านด่านภายใน 7 วัน → EXPIRED แล้วตกไปเป็นเรต ROPZ
milestoneส่งตอนผู้เล่นถึงจุดที่ถือว่าเข้าเกมแล้วจริง เช่น tutorial_done · level_2เป็นอีกทางหนึ่งที่ผ่านชั้น B โดยไม่ต้องรอเวลาเล่นสะสม · เกมที่จบไว ถ้าไม่ส่ง milestone จะเสียเปรียบ เพราะเหลือทางพิสูจน์ทางเดียว
ใช้ userId ของแพลตฟอร์มรับ id จาก SDK ไม่ใช่สร้างเอง · guest_uuid ต้อง merge เข้ากับบัญชีจริงตอนผู้เล่นสมัครเครดิตผูกกับคู่ (ผู้เล่น × เกม) · ถ้า id ไม่ตรง ผู้เล่นคนเดียวถูกนับเป็นสองคน ครึ่งหนึ่งของเครดิตที่คุณควรได้จะหายไป
โฆษณาผ่าน adapter ของ ROPZไม่เรียก SDK โฆษณาของตัวเองตรง ๆ · ส่ง ad_impression พร้อม adType / eCPM / revenueยอดต้อง reconcile กับที่ ad network จ่ายเข้ามาจริง และต้องตรวจว่าโฆษณาถูกดูจริงก่อนนับเงิน · ถ้าเรียกเอง เรา reconcile ไม่ได้ = จ่ายไม่ได้
การซื้อในเกม = ใช้เพชรผ่านกระเป๋ากลางเรียก spend API พร้อม gameId · ห้ามต่อ payment gateway เองผู้เล่นซื้อเพชรกับ ROPZ ไม่ใช่กับเกมของคุณ · ส่วนแบ่งของคุณเกิดตอนเพชรถูกใช้ในเกมของคุณ · ถ้าไม่ผ่าน API นี้ ระบบไม่มีบันทึกว่าเพชรถูกใช้ที่ไหน = แบ่งให้ไม่ได้
ห้ามให้ client ตัดสินอะไรที่เป็นเงินตัวเกมส่งได้แค่สัญญาณ · ห้ามคำนวณเรต ตัดสิน attribution หรือ grant ไอเทมเองจากฝั่งเครื่องผู้เล่นเครื่องผู้เล่นแก้ค่าได้ · ระบบทั้งหมดออกแบบให้เซิร์ฟเวอร์เป็นผู้ตัดสินเพราะเหตุนี้ · ถ้าตรวจพบ ผู้เล่นกลุ่มนั้นถูกตีเป็น REJECTED และพาร์ตเนอร์ถูกตั้งธง
build ตาม Build SpecWebGL โหมด Release · ขนาดไฟล์ตามที่สเปกกำหนด · ไม่เรียกทรัพยากรภายนอกนอกเหนือที่อนุญาตเป็นเงื่อนไขขึ้นลิสต์และรับส่วนแบ่ง ไม่ใช่คำแนะนำ · ไม่ผ่านด่านตรวจตอนส่งงาน = เกมยังไม่ถูกเปิดให้เล่น

2 · ฝั่ง Backend (เซิร์ฟเวอร์ของคุณ)

ต้องเพิ่มอะไรทำอะไรบ้างทำไมต้องมี — ถ้าไม่ทำจะเกิดอะไร
รับ event แบบ server-to-serverยืนยันสถานะกับเซิร์ฟเวอร์ ROPZ โดยตรง · อย่าเชื่อค่าที่ client ส่งมาให้เป็นข้อสรุปค่าที่ผ่านเครื่องผู้เล่นถือว่าปลอมได้เสมอ · ถ้าคุณ grant ของตามคำบอกของ client จะถูกดูดของฟรี และเป็นความเสียหายของคุณเอง ไม่ใช่ของเรา
Idempotency ทุก eventเก็บ eventId / refClickId แล้วตัดซ้ำ · รับ event เดิมซ้ำต้องได้ผลเท่าเดิมเครือข่ายพลาดแล้วยิงซ้ำเป็นเรื่องปกติ · ไม่ตัดซ้ำ = ตัวเลขเบิ้ล แล้วตอนกระทบยอดกับ Partner Portal จะไม่ตรง ซึ่งเข้าข่ายต้องตรวจสอบย้อนหลัง
ผูก userId แบบแยกรายเกมเก็บ mapping userId ของแพลตฟอร์ม ↔ ผู้เล่นในเกมคุณ โดยแยกตาม gameIdเรตของคุณมีผลเฉพาะเกมที่คุณพาผู้เล่นมา · ถ้าคุณมีหลายเกม การผูกรวมกันจะทำให้เครดิตข้ามเกมกัน ซึ่งระบบจะปฏิเสธตอนตรวจลายเซ็นของลิงก์
grant ของเมื่อได้ callback ยืนยันแล้วเท่านั้นรอผลยืนยันการหักเพชรจาก ROPZ ก่อน แล้วค่อยให้ของในเกมเพชรถูกหักที่ฝั่งเรา ไม่ใช่ฝั่งคุณ · ถ้าให้ของก่อนแล้วการหักล้มเหลว ของหลุดไปฟรีและเรียกคืนไม่ได้
รองรับ PENDING → CONFIRMED (จ่ายส่วนต่างย้อนหลัง 7 วัน)อย่าเพิ่งบันทึกรายได้ที่เรตสูงทันที · รอสถานะ CONFIRMED แล้วรับส่วนต่างย้อนหลังผู้เล่นที่คุณพามาเริ่มที่ PENDING และได้เรต ROPZ ไปก่อน จนกว่าจะผ่านด่านคุณภาพ · ถ้าคุณตั้งตัวเลขไว้ที่เรตสูงตั้งแต่วันแรก งบของคุณจะไม่ตรงกับเงินที่เข้าจริงทุกเดือน
รองรับการหักคืนย้อนหลังเก็บ log ระดับรายธุรกรรมว่าเพชรก้อนไหนถูกใช้กับอะไร ย้อนหลังได้ถึงราว 120 วันถ้าเกิดเคสต้องคืนเงินผู้เล่นจริง เราจะหักคืนตามสัดส่วนจากส่วนแบ่งที่จ่ายไปแล้ว · ไม่มี log = ตกลงกันไม่ได้ว่าหักเท่าไหร่ · log ชุดนี้คุณเปิดดูเองได้ใน Partner Portal
กระทบยอดกับ Partner Portal ทุกงวดเทียบยอดของระบบคุณกับตัวเลขในพอร์ทัล · ยึดตัวเลขฝั่ง ROPZ เป็นตัวตั้งต่างกันเล็กน้อยเป็นเรื่องปกติ (event ที่มาช้า · สถานะที่ยังไม่ CONFIRMED) · ที่ต้องระวังคือส่วนต่างที่โตขึ้นเรื่อย ๆ ซึ่งแปลว่ามี event หายหรือถูกนับซ้ำ · ควรจับให้ได้ในงวดแรก ๆ ไม่ใช่ตอนสิ้นปี
ประกาศ asset ที่ใช้จาก Base Kitส่ง manifest ว่าใช้ชิ้นไหนบ้าง พร้อม build ที่ส่งตรวจใช้ชิ้นเดียวก็นับว่าใช้ ไม่คิดตามสัดส่วน → ค่าแพลตฟอร์มขยับ +10% เฉพาะฝั่งที่คุณพาผู้เล่นมาเอง · ประกาศไม่ตรงกับสิ่งที่ตรวจเจอใน build = ผิดเงื่อนไขสัญญา ไม่ใช่แค่ปรับเรตย้อนหลัง

3 · ลำดับที่แนะนำให้ทำ

① ต่อ SDK + session_start ให้ผ่านก่อน แล้วทดสอบด้วยลิงก์ทดสอบจาก Partner Portal ว่าขึ้นเป็น dev พามาจริง → ② ใส่ heartbeat + milestone แล้วดูใน Portal ว่าผู้เล่นทดสอบเปลี่ยนจาก PENDING เป็น CONFIRMED ได้ → ③ ต่อฝั่งเงิน (โฆษณา / ใช้เพชร) พร้อม idempotency → ④ กระทบยอดรอบแรกกับ Portal ก่อนเปิดจริง ไม่ใช่หลังเปิด → ⑤ ค่อยส่ง build ให้ตรวจ · เกณฑ์ว่าเสร็จ = ผู้เล่นทดสอบ 1 คนเดินครบเส้นทาง แล้วยอดในระบบคุณตรงกับ Portal

ถ้า dev เลือกใช้ asset จากแพ็กนี้ = เราถือว่าเราร่วมออกแรงผลิตด้วย → ส่วนของ ROPZ +10% (เฉพาะเรตฝั่ง 🟢 dev พามาเอง) · ถ้า dev ทำอาร์ตเองทั้งหมด = ได้เรตตั้งต้น (เก็บได้มากกว่า) · dev เลือกเองได้ ไม่มีการบังคับ

จุดยืนที่ล็อกไว้แล้ว — นี่ไม่ใช่บทลงโทษ: เรตแบ่งรายได้สะท้อน "ใครลงแรงผลิต" · เราออก asset ให้ = เราร่วมผลิต = แบ่งเรามากขึ้น · dev เอาอาร์ตตัวเองมา = เขาเก็บมากขึ้น ตรงไปตรงมา

แล้วจะรู้ได้ยังไงว่า dev ใช้ asset เราจริง — ตรวจ 3 ชั้น

ปัญหาคือ dev มักบีบอัดไฟล์ (texture crunch / แปลงเสียงเป็น Vorbis) ทำให้ไฟล์เปลี่ยนไป → เทียบไฟล์ตรง ๆ ไม่ได้ ระบบจึงตรวจ 3 ชั้นซ้อนกัน:

A · ประกาศตอน build ชั้นหลัก

ตัวช่วย build สแกนโปรเจกต์ว่าอ้างถึง asset ชิ้นไหนของเราบ้าง แล้วเขียนเป็นไฟล์รายการที่เซ็นกำกับฝังไปกับตัวเกม

B · ตรวจซ้ำที่เซิร์ฟเวอร์ ตัวจับโกง

แกะภาพ/เสียงออกจากตัวเกมแล้วทำ ลายนิ้วมือเชิงการรับรู้ (perceptual hash) เทียบกับคลังของเรา — ทนต่อการบีบอัด จับได้ว่ารายการที่ประกาศมาโกหกหรือไม่

C · คลังกลาง

เก็บข้อมูล asset ทุกชิ้น (รหัส · ลายนิ้วมือ · ประเภท) เป็นแหล่งอ้างอิงเดียวของทั้งระบบ

ถ้าประกาศว่าไม่ใช้ แต่ตรวจแล้วเจอ → ตีกลับ/ตั้งธง · เจอย้อนหลังหลังจ่ายเงินไปแล้ว → เรียกคืนได้ (หลักการเดียวกับด่านคุณภาพในหัวข้อ 14)

11 ช่องทางที่ระบบใช้ตัดสิน

"ใครพามา" ไม่ใช่การเดา — ระบบจัดทุกผู้เล่นเข้า 1 ใน 11 ช่องทางนี้ · 7 ช่องแรกนับเป็น ROPZ พามา · 4 ช่องหลังนับเป็น dev พามา

🔵 ROPZ พามา (7 ช่อง) ค่าตั้งต้น

  1. เข้าตรง — พิมพ์ URL เอง / bookmark
  2. ค้นเจอในพอร์ทัล — หมวดหมู่ / ค้นหา / เกมแนะนำ
  3. เด้งจากเกมอื่น — โปรโมตข้ามเกมในพอร์ทัล
  4. แคมเปญคูปอง — ลิงก์คูปอง / พาร์ตเนอร์ B2B
  5. ช่องทาง RO — จากเกม RO อื่น / เว็บ Gravity / GNJOY
  6. ค้นเจอจาก Google — เข้าหน้าพอร์ทัลโดยไม่มีรหัสอ้างอิง
  7. โฆษณาที่ ROPZ ยิงเอง

🟢 Dev พามา (4 ช่อง) ต้องมีลิงก์

  1. ฝังเกมบนเว็บ dev — iframe + ลิงก์อ้างอิง
  2. โซเชียลของ dev — เพจ / YouTube / ชุมชน + ลิงก์
  3. ฐานผู้เล่นเดิมของ dev — ส่งคนเข้ามา + ลิงก์
  4. โฆษณาที่ dev ยิงเอง + ลิงก์

ทั้ง 4 ช่องต้องมีลิงก์อ้างอิงที่ระบบยืนยันได้ และ ต้องผ่านด่านคุณภาพก่อน จึงจะได้เรตสูง

กติกาที่ทำให้ระบบยุติธรรม: ค่าตั้งต้นคือ ROPZ พามา — dev ต้องพิสูจน์ว่าตัวเองพามา ถึงจะได้เรตสูง ไม่ใช่กลับกัน · ถ้าพิสูจน์ไม่ได้ ระบบถือว่าเป็นของ ROPZ โดยอัตโนมัติ (กันการอ้างสิทธิ์เกินจริง)

ขั้นตอนการตัดสิน — เกิดอะไรขึ้นตอนผู้เล่นกดเข้าเกม

ทำไมต้องตัดสินที่เซิร์ฟเวอร์: ถ้าให้ตัวเกม (ที่รันในเบราว์เซอร์ของผู้เล่น) เป็นคนบอกว่า "ผู้เล่นคนนี้ผมพามา" ก็แก้ไขได้ง่ายมาก · ระบบจึงให้ตัวเกมส่งได้แค่สัญญาณดิบ แล้วเซิร์ฟเวอร์เป็นคนตัดสินเองทั้งหมด
13กติกาสำคัญ

First-touch — ผูกครั้งเดียว และผูกแยกรายเกม

กติกานี้พาร์ตเนอร์ถามบ่อยที่สุด และเป็นสิ่งที่ทำให้การลงทุนคูปองของเราคุ้ม · มี 2 ครึ่งที่ต้องเข้าใจคู่กัน

ครึ่งแรก · ช่องทางแรกชนะ

ผู้เล่นเข้าเกมหนึ่งครั้งแรกทางไหน = ผูกกับช่องทางนั้น ไม่ทับของเดิม แม้เข้ามาทีหลังทางอื่น · ฝั่ง dev การผูกมีอายุ 12 เดือน (ต่อได้) ฝั่ง ROPZ เป็นค่าตั้งต้นจึงไม่มีวันหมด

ครึ่งหลัง · ผูกแยกรายเกม เคาะแล้ว

การผูกคิดเป็นคู่ (ผู้เล่น × เกม) ไม่ใช่ต่อผู้เล่นทั้งพอร์ทัล · พาร์ตเนอร์มี 5 เกม = สร้างลิงก์ 5 อัน แต่ละอันได้เครดิตเฉพาะเกมของตัวเอง

ทำไมต้อง "ช่องทางแรกชนะ"

ถ้าใช้ "ช่องทางล่าสุดชนะ" พาร์ตเนอร์จะแค่ยิงลิงก์ใส่ผู้เล่นที่เราหามาแล้ว เพื่อแย่งเครดิต — first-touch ปิดช่องนั้นตั้งแต่ต้น

ทำไมต้อง "แยกรายเกม"

ถ้าผูกทั้งพอร์ทัล พาร์ตเนอร์ที่พาผู้เล่นมาเกมเดียว จะได้เรตสูงจากเกมของพาร์ตเนอร์รายอื่นที่ตัวเองไม่ได้ลงแรงด้วย · แยกรายเกมทำให้เครดิตตรงกับแรงที่ลงจริง

เวลาที่ต้องนับ — เอกสารเก่ายัด 5 เรื่องไว้ในตัวเลขเดียว

สเปกเดิมเขียนแค่ว่า "window 30–90 วัน" ซึ่งคลุมหลายเรื่องที่ไม่ใช่เรื่องเดียวกัน · ถ้าไม่แยกให้ชัด จะคิดเงินผิดและเถียงกับพาร์ตเนอร์ทุกเดือน — นี่คือ 5 เวลาที่ต้องตั้งแยกกัน

คู่แข่งตั้งไว้กี่วัน — คำตอบตรง ๆ คือ "ไม่มีใครประกาศ"

Poki — ไม่ต้องนับเวลาเลย

Poki ตัดสินจากช่องทางของการเข้าครั้งนั้น (referrer ของ visit) ไม่ได้ผูกติดผู้เล่นไว้ล่วงหน้า — dev ได้ 100% เมื่อผู้เล่นเข้ามาตรง/bookmark/ค้นชื่อเกม/โซเชียลหรือชุมชนของ dev · Poki เก็บ 50% เมื่อมาจากการโปรโมตของ Poki

➡️ ไม่มี lookback ไม่มีอายุการผูก เพราะคิดใหม่ทุกครั้งที่เข้าเล่น

CrazyGames · GameDistribution — ไม่มีเรื่องนี้ในสัญญา

ทั้งสองเจ้าไม่ใช้เรตตาม "ใครพามา" เลย — GameDistribution จ่าย 33% คงที่ ทุกกรณี · CrazyGames ไม่ประกาศตัวเลข · จึงไม่มีเวลา attribution ให้อ้างอิง

⚠️ สรุปข้อเท็จจริง: ไม่มีพอร์ทัลเกมเว็บเจ้าไหนประกาศตัวเลข attribution window — เพราะ Poki ไม่จำเป็นต้องใช้ (คิดรายครั้งที่เข้าเล่น) และอีก 2 เจ้าไม่มีเรตแบบนี้ · เราจึงต้องตั้งเอง โดยยืมมาตรฐานจาก 2 อุตสาหกรรมข้างเคียงที่มีตัวเลขชัด

function attribute(session, user, gameId) {
  let source;
  if (session.ref && verifyRefSig(session.ref, gameId)   // ลายเซ็นต้องตรงกับ "เกมนี้"
                 && !refExpired(session.ref)) {
      source = mapDevChannel(session.ref.channelTag);    // #8-11 (DEV)
  } else if (session.campaignId || isInternalReferrer(session.referrer)) {
      source = mapRopzChannel(session);                  // #1-5 (ROPZ)
  } else {
      source = "ROPZ_ORGANIC";                           // #6 ค่าตั้งต้น
  }
  // FIRST-TOUCH ต่อคู่ (ผู้เล่น × เกม) — ผูกครั้งเดียว ไม่ทับของเดิม
  const key = user.id + ":" + gameId;
  if (!attribution[key]) {
      attribution[key] = {
        source,
        acquiredAt: session.ts,
        partnerId : isDev(source) ? session.ref.partnerId : null,
        refClickId: isDev(source) ? session.ref.clickId   : null,
        status    : isDev(source) ? "PENDING" : "CONFIRMED"
      };
  }
  return attribution[key];   // เรต dev มีผลเฉพาะเกมนี้
}

function revenueSplit(event, user, gameId) {
  const a = attribution[user.id + ":" + gameId];
  const isDevConfirmed = isDev(a.source) && a.status === "CONFIRMED";
  const bucket = isDevConfirmed ? "DEV" : "ROPZ";   // PENDING/EXPIRED = เรต ROPZ ชั่วคราว
  const r = RATE[event.type][bucket];
  // มติ 11 ส.ค. 2026: แบ่งจากยอดเต็ม ไม่หักค่าธรรมเนียมก่อน
  // dev จึงได้ % ของยอดเต็ม · ค่าธรรมเนียมออกจากส่วนของ ROPZ
  const gross = event.type === "iap" ? event.gross : event.revenue;
  const fee   = event.type === "iap" ? event.gatewayFee : 0;
  return { partner: gross * r.dev, ropz: gross * r.ropz - fee };
}

อภิธานศัพท์ (สำหรับฉบับพิมพ์)

dev / พาร์ตเนอร์
นักพัฒนาเกมภายนอกที่เอาเกมมาลงพอร์ทัลเรา ในเอกสารนี้ "dev" กับ "พาร์ตเนอร์" คือคนเดียวกัน
Ads / โฆษณา
รายได้จากโฆษณาที่แสดงในเกม เช่น ดูคลิปจบแล้วได้รางวัล (rewarded) หรือโฆษณาคั่นจอ (interstitial)
IAP In-App Purchase
การเติมเงินซื้อของในเกม เช่น ซื้อเพชร ซื้อชุด
Rev-share ส่วนแบ่งรายได้
ข้อตกลงว่ารายได้ที่เกิดขึ้นจะแบ่งกันคนละกี่ % ระหว่าง ROPZ กับ dev
Attribution "ใครพาคนมา"
กระบวนการตัดสินว่าผู้เล่นคนหนึ่งเข้ามาในระบบผ่านช่องทางของใคร นี่คือหัวใจของเอกสารนี้
Platform Fee
ส่วนที่ ROPZ หักจากรายได้ของเกม เป็น "ค่าใช้แพลตฟอร์ม" — เรตนี้แหละที่ขยับตาม attribution
CAC Customer Acquisition Cost
ต้นทุนในการหาผู้เล่น 1 คนเข้ามา เช่น ค่ายิงโฆษณา ค่าคูปองที่แจก
ARPU Average Revenue Per User
รายได้เฉลี่ยต่อผู้เล่น 1 คน (ในเอกสารนี้คิดเป็นต่อปี)
MAU / DAU
จำนวนผู้เล่นที่เข้ามาใน 1 เดือน / 1 วัน — ใช้วัดขนาดฐานผู้เล่น
eCPM
รายได้โฆษณาต่อการแสดงผล 1,000 ครั้ง ยิ่งสูงยิ่งดี — ของไทย/SEA ต่ำกว่าอเมริกา/ยุโรปมาก
Retention D1 / D7 / D30
% ผู้เล่นที่กลับมาเล่นอีกในวันถัดไป / 7 วัน / 30 วัน — เป็นตัวชี้ว่าเกมสนุกจริงไหม
ref link ลิงก์อ้างอิง
ลิงก์พิเศษที่มีรหัสพาร์ตเนอร์ติดอยู่ (?ref=…) ใช้พิสูจน์ว่า "ผู้เล่นคนนี้ dev พามาเอง"
First-touch
กติกาที่ยึด "ช่องทางแรก" ที่ผู้เล่นเข้ามา แล้วผูกไว้ตลอด ไม่เปลี่ยนตามหลัง
Quality gate ด่านคุณภาพ
ด่านตรวจว่าผู้เล่นที่ dev อ้างว่าพามาเป็น "คนจริงที่เล่นจริง" ไม่ใช่บอทหรือคลิกฟาร์ม
