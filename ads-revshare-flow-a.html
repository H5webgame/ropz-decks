4 · โครงสร้าง ad unit — แยกพาร์ทเนอร์ยังไง

ไม่ตั้ง ad unit แยกรายเกม (50 เกม = 50 unit จัดการไม่ไหว + eCPM ผันผวนเพราะ volume น้อย) แต่ใช้ placement ตายตัวไม่กี่ตัว แล้วแยกเกมด้วย custom dimension

Placement IDนำมาแบ่งคำอธิบาย
ropz_rewarded_ingame✓ แบ่งRewarded video ท้ายเกม (จุดที่ผู้เล่นกดรับ Poring Coin)
ropz_interstitial_ingame✓ แบ่งInterstitial ระหว่างด่าน/จบรอบ
ropz_banner_portal✕ ไม่แบ่งแบนเนอร์หน้ารวมเกม — ROPZ ล้วน
ropz_house_ad✕ ไม่แบ่งโปรโมตเกมในเครือ/อีเวนต์ — ROPZ ล้วน

ทุก ad request แนบ gameId ของเกมที่ผู้เล่นอยู่ ณ ขณะนั้นเป็น key-value → รายงานของ network แตกยอดตาม dimension นี้ → back-office map เข้าเกมได้โดยไม่ต้องเชื่อ client

ต้องแก้สเปกเดิม: ปัจจุบัน ROPZ_Attribution_SDK_Spec_260715.md §3 ให้ client ยิง event ad_impression พร้อม payload eCPM, revenue แล้ว §7 เอา event.revenue ไปคูณเรตตรง ๆ — ใช้ไม่ได้กับ Flow A เพราะเงินจริงอยู่ที่ network ไม่ใช่ที่ client (ปลอมได้ + ไม่มีวันตรง statement)
→ เปลี่ยนเป็น: client ยิงแค่ สัญญาณ (gameId, placementId, adType) · เงินมาจาก event ใหม่ ad_revenue_reconciled ที่ดึงจาก reporting API ของ network แบบ server-to-server รายวัน · คิดส่วนแบ่งเป็น รอบเดือน ไม่ใช่ราย event

5 · ⚠️ กรอบสัญญา — จุดที่พลาดไม่ได้

นโยบาย AdSense ระบุว่า ห้ามแบ่งรายได้จากบัญชีให้บุคคลที่สาม เว้นแต่ได้รับอนุญาตเป็นลายลักษณ์อักษร และ Google ระบุเองว่า “rarely give publishers permission”

แต่ Poki / CrazyGames / GameDistribution ทำได้ เพราะ กรอบความสัมพันธ์ไม่ใช่ “แบ่งรายได้โฆษณา” — เขาเป็น publisher เจ้าของเว็บ ส่วน dev คือ ผู้ให้สิทธิ์คอนเทนต์ที่ได้รับค่าลิขสิทธิ์ (content royalty) เว็บเป็นของแพลตฟอร์ม เกมเป็นคอนเทนต์ที่ฝังอยู่ ไม่ใช่ “เว็บของบุคคลที่สาม”

❌ ห้ามเขียนแบบนี้
“ROPZ แบ่งรายได้จากบัญชีโฆษณาให้พาร์ทเนอร์ X%”
“ส่วนแบ่งรายได้ AdSense”
✅ เขียนแบบนี้
“พาร์ทเนอร์ให้สิทธิ์ ROPZ เผยแพร่เกมบนพอร์ทัล และได้รับ ค่าลิขสิทธิ์ คำนวณจาก Net Ad Revenue ที่เกิดจากเกมนั้นในอัตรา X%”

ฐานคำนวณต้องเป็น Net Ad Revenue = เงินที่ ROPZ ได้รับจริง หลังหักส่วนแบ่ง network/mediation, ยอดที่ถูกตัดจาก IVT และการปรับปรุงย้อนหลัง — ไม่ใช่ยอดประมาณการจาก eCPM

6 · สิ่งที่ต้องสร้างเพิ่ม (ต้นทุนของการเลือก A)

หัก ณ ที่จ่าย + VAT + ฟอร์มภาษีตอน onboard (ในประเทศ/ต่างประเทศคนละแบบ)
🔗 Reconciliation
ดึงรายงาน network รายวันตาม gameId · กระทบยอดกับ statement · เก็บ log ไว้ตรวจย้อนหลัง
📊 Developer Portal
หน้ารายได้ให้ dev เห็น: impression · revenue · payout status
ทุกเจ้าเป็น trust-based — ไม่มีใครให้ dev เห็นบัญชี network ตรง
💵 Cash float
network จ่าย NET-30/60 แต่เราต้องจ่าย dev ตามรอบ — ต้องมีเงินหมุนคั่นกลาง
↩️ Clawback
ถ้า network หักคืนเพราะ IVT หลังจ่ายไปแล้ว ต้องหักกลบจากรอบถัดไปได้

8 · ความเสี่ยงของ A และวิธีคุม

ความเสี่ยงวิธีคุม
Dev ไม่เชื่อตัวเลข (เห็นแค่ที่เราบอก)statement รายเกนละเอียด + สิทธิ์ขอตรวจ (right-to-audit) เขียนในสัญญา · ทุกเจ้าใหญ่ก็ trust-based เหมือนกัน
บัญชีเดียวโดนแบน = ตายทั้งระบบต่อ network สำรองไว้อย่างน้อย 2 เจ้า + ผ่าน mediation เพื่อสลับได้ทันที · ad-verification คัด IVT ก่อนถึง network
เราแบกภาระคนกลางทางการเงินใช้ผู้ให้บริการ payout สำเร็จรูป (Tipalti-style) แทนเขียนเอง · ตั้ง cash float ตามรอบ NET
ยอดไม่ตรงกับ networkยึด statement ของ network เป็นข้อมูลจริงเมื่อไม่ตรง — เขียนไว้ในสัญญาชัด ๆ

9 · ทางอัปเกรดในอนาคต — MCM

ถ้าวันหนึ่งภาระ payout/ภาษีหนักเกิน มีทางออกที่เป็นผลิตภัณฑ์ทางการของ Google: MCM (Multiple Customer Management) ใน Google Ad Manager

  • ROPZ = parent publisher · dev = child publisher
  • โหมด “Manage Inventory” — ROPZ ยังคุม inventory และ ad serving ทั้งหมด แต่ ไม่ต้องเข้าถึงบัญชี dev
  • ตกลงส่วนแบ่งได้ 0–100% แล้ว Google จ่ายเงินตรงให้ทั้งสองฝ่ายเอง (auto-payment)

= ได้ข้อดีของ A ทั้งหมด โดยตัดภาระคนกลางทางการเงินออก · ข้อแลก: ต้องใช้ Google Ad Manager และ dev ต้องมีบัญชีของตัวเอง (onboard ช้าลง)
Y8 คือเจ้าที่ทำแบบนี้อยู่แล้ว (เปิด AFP ให้ dev เลือกคู่กับ SDK ปกติ) — เป็น precedent ว่าทำสองทางพร้อมกันได้

10 · สิ่งที่ต้องทำต่อ

🛠️ Engineering
  • เพิ่ม adUnitId / placementId ใน ad_placement
  • ส่ง adConfig ตอน init
  • แนบ gameId เป็น custom dimension ทุก ad request
  • ทำ job ดึง reporting API รายวัน (server→server)
  • แก้ revenueSplit() เป็นคิดรอบเดือน
⚖️ Legal
  • ร่างสัญญาเป็น content licensing / royalty
  • นิยาม Net Ad Revenue
  • ข้อ clawback + right-to-audit
  • ข้อห้ามใส่โค้ดโฆษณาในบิลด์
  • ระยะเวลาแจ้งล่วงหน้าเมื่อเปลี่ยนเรต
💼 Finance
  • เคาะ NET / ขั้นต่ำ / สกุลเงิน
  • เลือกผู้ให้บริการ payout
  • ฟอร์มภาษี in/out ประเทศ
  • ตั้ง cash float ตามรอบ NET
  • ทบทวนโมเดล P&L ให้ใช้ฐาน net (เดิมใช้ gross ฿60/user/ปี)
อย่าลืม: โมเดล P&L เดิมใน ROPZ_Attribution_RevShare_Spec_260714.md ตั้งบน Ad revenue (gross) ฿60/user/ปี — พอเปลี่ยนฐานเป็น net ตามเอกสารนี้ ตัวเลข ROPZ share จะลดลงตามส่วนแบ่ง network ต้องอัปเดตโมเดลก่อนเอาไปใช้ตัดสินใจงบ
